# Зональная аналитика: нагрузка по часам + курьерские зоны города

**Дата:** 2026-06-27
**Ветка:** phase1-backend-ingest
**Статус:** дизайн утверждён, готов к плану реализации

## Проблема

Текущая аналитика «корявая, много бесполезного». Заказчику нужен чёткий
зональный взгляд:

1. **Кухня** — нагрузка по часам по зонам **Пицца / Япония / Горячее** (объём + среднее время готовки).
2. **Курьер** — нагрузка по **зонам города** (районам), а не по конкретным точкам.

Существующие блоки аналитики **не сносим** — добавляем зональный экран сверху как основной.

## Контекст (как устроено сейчас)

- `OrderItem.station` (`rolls|pizza|hot|other`) — кухонная зона блюда. **Хранится после merge `hot→pizza`** (`stations.py:ZONE_MERGE`), поэтому из БД горячее отдельно не вытащить.
- `Order` имеет `address`, `address_lat`, `address_lon`, `assigned_courier_code/name`, `on_way_at`, `delivered_at`. **Поля «зона/район доставки» нет.**
- Доставка определяется типом события iiko (`DeliveryOrderUpdate`), не полем заказа.
- Время хранится в UTC; локализация на UTC+5 (`config.iiko_tz_offset_hours=5`) при расчёте по дням/часам.
- Аналитика: `backend/app/analytics_stages.py` + эндпоинты `backend/app/api.py` (`/admin/...`); фронт `frontend/src/screens/Analytics.jsx`, зоны `frontend/src/lib/zones.js`.

## Зоны

Зоны = **Пицца, Япония, Горячее** (кухня, 3 зоны) + **Курьер** (доставка, разбита на районы города).
Лейблы: `pizza`→Пицца, `rolls`→Япония, `hot`→Горячее.

---

## Решение

### A. Отделение «Горячее» от «Пицца»

**Новая колонка `OrderItem.kitchen_zone: str|None`** — до-merge зона (`rolls|pizza|hot|other`).
- Проставляется при приёме заказа: резолвер зоны вычисляет зону **до** `merge_zone`, пишем её в `kitchen_zone`, а в `station` остаётся слитая (для рассылки на планшеты — без изменений).
- Реализация: `build_resolver` возвращает и raw-зону, и merged; ingest сохраняет обе.
- **Бэкфилл** существующих строк: одноразовый скрипт пересчитывает `kitchen_zone` по `OrderItem.name` через `classify_name`/`classify_product`. Где имя зону не даёт — оставляем равной `station`.
- Аналитика кухни группирует по `kitchen_zone` (fallback на `station`, если NULL).

`station` (поведение кухни/планшетов) **не трогаем** — меняем только источник для аналитики.

### B. Курьерские зоны города (полигоны)

**Новая таблица `DeliveryZone`:**
```
id: int PK
org_id: str (index)        # филиал
name: str                  # «Центр», «Левый берег» и т.д.
polygon: JSON              # GeoJSON-подобный список [[lat, lon], ...]
color: str                 # цвет на карте/в таблице
created_at, updated_at
```

**Редактор зон** — отдельный экран в админке:
- Карта **Leaflet + leaflet-draw**, тайлы OSM.
- Рисуем/правим/удаляем полигоны, задаём имя и цвет.
- CRUD-эндпоинты: `GET/POST/PUT/DELETE /admin/delivery-zones` (фильтр по `org_id`).

**Привязка заказа к зоне — на лету при запросе аналитики** (не храним в заказе):
- Для каждого доставочного заказа с `address_lat/lon` — point-in-polygon (ray-casting) по списку зон филиала.
- Заказ без координат или вне всех зон → псевдо-зона **«Без зоны»**.
- Плюс: при перерисовке полигонов историческая аналитика пересчитывается под актуальную карту.
- Минус: расчёт на каждый запрос; приемлемо (десятки–сотни заказов за период), point-in-polygon дешёвый.

### C. Метрики нагрузки

**Кухня — нагрузка по часам (`зона × час`):**
- Объём = число блюд (`OrderItem`), у которых `station_ready_at` (или `station_accepted_at`) попал в этот час.
- Среднее время = средняя готовка (`station_accepted_at → station_ready_at`) по блюдам зоны в этом часу.
- Час — локальный (UTC+5), как в `sla_breaches`.
- Зоны строк: pizza, rolls, hot (по `kitchen_zone`). По умолчанию `other` **не показываем** (это не одна из трёх зон); вынести отдельной строкой — на подтверждение при ревью.

**Курьер — нагрузка по районам (`район × час`):**
- Объём = число доставленных заказов, привязанных к району, чей `on_way_at` (момент выезда) попал в час. (Час по выезду — момент, когда курьер уходит в район.)
- Среднее время = средняя доставка (`on_way_at → delivered_at`) по заказам района в этом часу.

## API

Новые эндпоинты (query: `org_id`, `from`, `to` — как у существующих):

1. `GET /admin/zone-load` — кухонная нагрузка по часам.
   ```
   { zones: ["pizza","rolls","hot"],
     hours: [0..23],
     cells: { "pizza": { "12": {count, avg_sec}, ... }, ... },
     totals_by_zone: { "pizza": {count, avg_sec}, ... } }
   ```
2. `GET /admin/courier-zone-load` — курьерская нагрузка по районам и часам.
   ```
   { zones: [{id, name, color}, ..., {id:null, name:"Без зоны"}],
     hours: [0..23],
     cells: { "<zoneId>": { "12": {count, avg_sec}, ... } },
     totals_by_zone: { "<zoneId>": {count, avg_sec} } }
   ```
3. `GET/POST/PUT/DELETE /admin/delivery-zones` — CRUD полигонов.

Расчёты — в `analytics_stages.py` (чистые функции над списком заказов/блюд, тестируемые без БД), эндпоинты — тонкие обёртки в `api.py`.

## Frontend

- **`frontend/src/screens/Analytics.jsx`** — добавить сверху два блока:
  - «Нагрузка по зонам кухни» — таблица-хитмап `зона × час`, в ячейке объём + ср.время; подсветка интенсивности по объёму.
  - «Курьер: нагрузка по районам» — аналогичная таблица `район × час`.
- **Новый экран `DeliveryZones.jsx`** — редактор полигонов на Leaflet (+ leaflet-draw), список зон, CRUD.
- `frontend/src/lib/zones.js` — лейблы/цвета кухонных зон (есть); добавить хелперы для курьерских зон.
- `frontend/src/lib/api.js` — вызовы новых эндпоинтов.
- Старые блоки (этапы/SLA/лаг/аномалии/журнал) остаются ниже без изменений.

## Зависимости

- Frontend: `leaflet`, `leaflet-draw` (или `react-leaflet` + draw). Тайлы OSM (бесплатные, требуют корректного User-Agent/attribution).
- Backend: point-in-polygon собственной реализацией (ray-casting), без тяжёлых геозависимостей вроде shapely.

## Тестирование

- `tests/test_zone_load.py` — кухонная нагрузка: раскладка блюд по часам/зонам, корректный fallback `kitchen_zone→station`, локальный час UTC+5.
- `tests/test_courier_zones.py` — point-in-polygon (внутри/снаружи/на границе), привязка заказа, «Без зоны», агрегация по районам/часам.
- `tests/test_kitchen_zone_backfill.py` — пересчёт `kitchen_zone` по имени, что `hot` отделяется от `pizza`.
- Существующие тесты аналитики не должны ломаться (старые блоки не трогаем).

## Миграции БД

- `OrderItem.kitchen_zone` (nullable) + индекс не обязателен.
- Таблица `delivery_zones`.
- Способ миграции — как принято в проекте (проверить: Alembic или авто-`create_all`). Бэкфилл `kitchen_zone` — отдельный скрипт/команда.

## Вне объёма (YAGNI)

- Не сносим и не переписываем существующие блоки аналитики.
- Не храним зону доставки в заказе (считаем на лету).
- Не делаем полигоны-зоны для кухни — кухонные зоны определяются блюдом, не геометрией.
- Не трогаем логику рассылки на планшеты (`station`/merge остаются).

## Открытые вопросы для ревью спека

- Показывать ли `other` отдельной строкой в кухонной нагрузке.
- Час курьера считать по `on_way_at` (выезд) — подтвердить, что это нужная точка отсчёта, а не `created_at`/`delivered_at`.
