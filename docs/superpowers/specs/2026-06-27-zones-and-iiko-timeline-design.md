# Авто-зоны спроса + наполнение аналитики из iiko

Дата: 2026-06-27

## Проблема

1. «Карта спроса» показывает кружки по числу заказов; нужно видеть **зоны**, без чисел.
2. Зоны рисуются вручную полигонами — нужно **авто-деление**.
3. В аналитике дублируется спрос-в-числах («Курьер · нагрузка по районам») — убрать.
4. Этапы «Очередь / Ожидание / Доставка» в аналитике пустые («0 доставок»), потому
   что тайм-штампы ставятся только по нажатию кнопок в KDS, а курьеры не тапают.
   Надо **тянуть тайм-штампы из iiko**, чтобы этапы заполнились.

## Решение

### 1. Авто-сетка зон (backend)

`POST /admin/zones/auto-grid?org_id=&n=6`:
- bbox по координатам заказов (`address_lat/lon`); если точек < 2 — дефолт Астана
  (`[51.0..51.3, 71.2..71.7]`), с паддингом ~5%.
- режем bbox на `n×n` равных клеток; каждая клетка → строка `DeliveryZone`
  (`name` = `A1..`, `polygon` = 4 угла `[lat,lon]`, `color` нейтральный,
  `auto_generated=true`).
- старые `auto_generated=true` зоны org удаляем и пересоздаём; ручные не трогаем.
- переиспользует `geo.assign_zone` и `courier_zone_load` без изменений.

Новая колонка `delivery_zones.auto_generated BOOLEAN DEFAULT FALSE` через
`_ADDED_COLUMNS` (SQLite-aware миграция уже есть).

### 2. Карта спроса (`/demand`) — только зоны

- Новый/расширенный эндпоинт даёт зоны + плотность (кол-во заказов в клетке).
- Рисуем клетки прямоугольниками (`L.rectangle`), заливка по плотности
  зелёный→оранжевый→красный; **без цифр** в подписи.
- Убираем кружки-по-счёту и заголовок «N заказов».
- Кнопка «Авто-разбить на зоны» → POST auto-grid → перерисовка.

### 3. Аналитика — убрать спрос-в-числах

Удаляем блок «Курьер · нагрузка по районам» (`courierLoadData` heatmap) из
`Analytics.jsx`. Кухонный heatmap, путь заказа, SLA, аномалии, журнал остаются.

### 4. Наполнение аналитики из iiko

Маппинг тайм-штампов заказа iiko Cloud → наши поля:

| iiko | наше поле | этап |
|------|-----------|------|
| `whenCreated` | `created_at` (только при вставке) | старт «Очереди» |
| `whenCookingCompleted` | `assembled_at` (fallback) | конец «Сборки» |
| `whenSended` | `on_way_at` (fallback) | «Ожидание» / старт «Доставки» |
| `whenDelivered` | `delivered_at` (fallback) | «Доставка» |

- `NormalizedOrder` + `normalize_full_order`: читать поля защитно (несколько
  кандидатов-ключей), парсить `_parse_iiko_local_to_utc`.
- `ingest_order`: писать по правилу **«только если поле пусто»** (тап в KDS
  приоритетен; iiko заполняет пустое). `created_at` из `whenCreated` лишь при
  первой вставке.
- Зал/вынос (`DineIn`/`Takeaway`): доставочные поля не трогаем.
- Диагностический лог сырых значений тайм-штампов (как уже есть для адреса) —
  чтобы сверить точные имена полей на реальном заказе.

## Риск

Имена полей зависят от версии Transport API (`whenSended` vs `whenSent`).
Чтение защитное + лог → после первого реального заказа сверяем и фиксируем.

## Вне scope

- Кластеры/секторное деление зон (выбрана сетка).
- Запись статусов обратно в iiko (`change_delivery_status` запрещён ключом).
