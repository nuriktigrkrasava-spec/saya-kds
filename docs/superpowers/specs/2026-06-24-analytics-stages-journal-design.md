# Спека 2 (аналитика, часть 1): Этапы заказа, бутылочное горло и журнал действий

**Дата:** 2026-06-24
**Статус:** утверждён дизайн, ждёт вычитки
**Часть большой подсистемы «Аналитика» (п.4).** Следующие спеки: дашборды по направлениям (выручка, курьеры, и т.д.) — переиспользуют данные отсюда.

## 1. Цель

Управляющий должен видеть **на каком этапе заказ застревает** (кухня / сборка / ожидание курьера / доставка), сводно за любой период, и иметь **журнал «кто что когда сделал»** по каждому заказу с drill-down. Сегодня аналитика тонкая: всё «за сегодня» или «за всё время», без выбора периода, без разбивки по этапам, а `order_events` пишется (только iiko-вызовы), но **нигде не читается**.

В scope этой спеки (утверждено заказчиком):
- **Ядро:** этапы каждого заказа с длительностями + подсветка «бутылочного горла»; сводка по этапам за период (avg/median/p95); журнал действий с фильтрами и drill-down.
- **Добавки:** лаг «готов→выехал»; SLA-просрочки (порог, тренд по дням, пиковые часы); кухня по зонам и сотрудникам; аномалии/накрутка.

## 2. Подход (гибрид)

- **Числовая аналитика этапов считается из таймстампов**, которые уже есть на `Order`/`OrderItem`. → Работает для **всех заказов, старых и новых** сразу: «добор истории из старых таймстампов» получается бесплатно, без миграции данных.
- **Журнал «кто именно»** строится из событий `order_events` (вперёд, с актором) + **синтез из таймстампов** для заказов, созданных до внедрения (там, где актор не сохранялся, поле «кто» пустое).

Разделение ответственности: цифры и графики → таймстампы (полная история); «кто что сделал» → события (вперёд) + синтез прошлого.

### 2.1 Таймстампы-источники (существующие, не меняем)
- `Order`: `created_at`, `assembled_at`, `on_way_at`, `delivered_at`, `total`, `org_id`, `number`, `service_type`.
- `OrderItem`: `station` (зона), `station_accepted_at`, `station_ready_at`, `checked_at`, `checked_by`.
- `order_events`: события (после Спеки 1 — все действия, см. §4.1).

## 3. Этапы заказа

Этап = пара таймстампов; длительность в секундах. На уровне заказа:

| # | Этап | Начало → Конец |
|---|------|----------------|
| 1 | Очередь на кухню | `created_at` → **min** `item.station_accepted_at` |
| 2 | Готовка | **min** `accepted` → **max** `item.station_ready_at` |
| 3 | Сборка | **max** `ready` → `assembled_at` |
| 4 | Ожидание курьера (лаг готов→выехал) | `assembled_at` → `on_way_at` |
| 5 | Доставка | `on_way_at` → `delivered_at` |
| 6 | Закрытие в iiko | `delivered_at` → close-событие (`order_events` type `iiko_write`, method `close`, ok=true) |

Правила:
- Этап со **`None`** на любом конце → длительность `null` (этап ещё не наступил / данных нет); в агрегатах такие пропускаются.
- **Бутылочное горло заказа** = этап с максимальной не-null длительностью.
- Отрицательные длительности (рассинхрон часов/правки) клампим в `0` и помечаем флагом `clamped` в ответе timeline (для честности).

## 4. Данные

### 4.1 Расширение `OrderEvent` (`backend/app/models.py`)
Добавить колонки (все nullable, чтобы не ломать существующие строки `iiko_write`):
- `org_id: str | None` (index)
- `actor_code: str | None`
- `actor_name: str | None`
- `item_id: int | None`

Существующие поля: `id, order_id, type, payload(JSON), at`. Индекс: `ix_order_events_org_at (org_id, at)`.
Прод-миграция — через `_ADDED_COLUMNS` в `main.py` (идемпотентный ALTER), как уже делается.

### 4.2 Универсальный логгер действий (`backend/app/api.py`)
Обобщить текущий `_log_iiko_event` в:
```
_log_action(session, order, type: str, *, actor_name="", actor_code="",
            item_id=None, payload=None) -> None
```
- Пишет `OrderEvent(order_id=order.id, org_id=order.org_id, type=type,
  actor_name=actor_name, actor_code=actor_code, item_id=item_id, payload=payload or {})`.
- `_log_iiko_event` остаётся тонкой обёрткой над `_log_action` (type="iiko_write"), чтобы не трогать вызовы из Спеки про iiko.

### 4.3 Набор типов событий (константы)
`item_accept, item_ready, item_check, item_revert, order_assemble, assign_courier, take, delivered, iiko_write`.
Вызовы `_log_action` добавить в соответствующие эндпоинты (`item_accept/ready/check/revert`, `order_assemble`, `order_assign_courier`, `order_take`, `order_delivered`). Актор = `body.by` (или `item.checked_by`), `item_id` — для item-событий.

### 4.4 Сервис этапов (`backend/app/analytics_stages.py`, новый)
Чистые функции над списком заказов (с `selectin` items), без сетевых вызовов:
- `order_stages(order) -> list[Stage]` — 6 этапов с длительностями, бутылочное горло, флаг `clamped`. `Stage = {key, label, seconds|None, bottleneck: bool}`.
- `stage_aggregates(orders) -> dict` — по каждому этапу avg/median/p95 (по не-null), распределение бутылочных горл (счётчик по этапам).
- `sla_breaches(orders, threshold_sec) -> dict` — полное время `created→delivered`; доля и список просрочек; разбивка по дню (`date`) и по часу (`created_at.hour`).
- `pickup_lag(orders) -> dict` — статистика этапа 4 (`assembled→on_way`): avg/median/p95 + список худших.
- `kitchen_zones(orders) -> dict` — по `item.station`: avg/median prep (`accepted→ready`); вложенно по `checked_by`.
- `anomalies(orders) -> list` — быстрые «готово» (`prep < 60s`, как сейчас) + заказы с ≥2 событиями `item_revert` (из `order_events`); каждая запись ссылается на `order_id`/`number`/актора.

Медиана/p95 — на чистом Python (`statistics`), без новых зависимостей в бэкенде.

## 5. API (новые эндпоинты, `backend/app/api.py`)

Общие query-параметры: `org_id` (обязателен, как у текущих admin-эндпоинтов), `from` и `to` (ISO-дата `YYYY-MM-DD`, включительно; дефолт — последние 7 дней). Доступ — `RequireManager`, как у прочих `/admin/*`.

- `GET /admin/orders/{order_id}/timeline` → `{order: {...}, stages: [Stage], events: [{at, type, actor_name, item_id, payload}]}`. `events` — merge реальных строк `order_events` и синтезированных из таймстампов (для заказов без событий).
- `GET /admin/stage-stats?org_id&from&to&sla_minutes=45` → `{stage_aggregates, bottleneck_distribution, sla: {...}, pickup_lag: {...}}`.
- `GET /admin/kitchen-zones?org_id&from&to` → `kitchen_zones(...)`.
- `GET /admin/journal?org_id&from&to&actor&type&order_number&limit&offset` → `{rows: [{at, order_number, type, actor_name, item_name|null, detail}], total}`. Источник — `order_events` (фильтры по индексам `org_id`/`at`/`type`), плюс синтез прошлого для диапазона до первого события.
- `GET /admin/anomalies` — расширить существующий: добавить возвраты ≥2 и ссылки; сохранить обратную совместимость текущего ответа (поля не убирать, только добавить).

Период-фильтр заказов — общий хелпер `_orders_in_period(session, org_id, dt_from, dt_to)` (по `Order.created_at`), переиспользуется всеми эндпоинтами.

## 6. Фронт (`frontend/src/`)

- Новая зависимость: **Recharts** (`npm i recharts`) — бары/линии/пай.
- Новый экран управляющего **`screens/Analytics.jsx`**, маршрут `/analytics` под `RequireManager` (добавить в `App.jsx` и в навигацию управляющего, рядом с `/dashboard`, `/admin`).
- Состав экрана (пикер периода сверху — пресеты «Сегодня / 7 дней / 30 дней / произвольно»):
  1. **«Где застревают»** — бар-чарт avg/p95 по 6 этапам + пай распределения бутылочных горл.
  2. **SLA** — KPI % просрочек + линия тренда по дням + бары по часам (пиковые часы).
  3. **Лаг готов→выехал** — KPI + топ худших заказов.
  4. **Кухня по зонам** — бары времени готовки по зонам, drill-down по сотрудникам.
  5. **Аномалии** — таблица (быстрые «готово» + возвраты) со ссылкой на тайм-лайн.
  6. **Журнал** — таблица с фильтрами (сотрудник/тип/заказ/период) + строка «открыть тайм-лайн заказа» → модалка/панель `timeline` с этапами и событиями.
- API-обёртки — в `frontend/src/lib/api.js`, в стиле существующих вызовов.

## 7. Производительность
- Эндпоинты считают по выборке заказов за период (`created_at` в диапазоне) с `selectin` items — без N+1. Период по умолчанию 7 дней ограничивает объём. Пагинация только у `journal`.
- Никаких новых фоновых задач/хранилищ — всё считается на запрос.

## 8. Вне scope этой спеки
- Дашборд выручки/среднего чека/типов оплаты (отдельная спека — данные `total`/`payments` уже есть).
- На-курьера агрегаты времён доставки (следующая спека «курьеры»).
- Стоп-листы (частота/длительность out-of-stock) — отдельная спека.
- Экспорт новых отчётов в CSV сверх текущего `report.csv`.

## 9. Тестирование
- **Сервис этапов (юнит, без сети):** заказ с полным набором таймстампов → корректные 6 длительностей + правильное бутылочное горло; этап с `None`-концом → `null`; отрицательная длительность → клампится в 0 с флагом; агрегаты avg/median/p95 на маленькой выборке; SLA-порог (просрочен/нет, разбивка по дню/часу); pickup_lag; kitchen_zones по зонам и сотрудникам; anomalies (быстрые + возвраты).
- **Логгер действий:** каждый lifecycle-эндпоинт пишет `OrderEvent` с правильными type/actor/item_id/org_id; `_log_iiko_event` по-прежнему работает.
- **API:** `stage-stats`/`kitchen-zones`/`journal`/`timeline` — period-фильтр, фильтры журнала, пагинация; `timeline` мёржит реальные и синтезированные события; `anomalies` обратно совместим.
- **Фронт:** сборка `npm run build` зелёная с Recharts; ручная проверка экрана `/analytics` на seed-данных.
